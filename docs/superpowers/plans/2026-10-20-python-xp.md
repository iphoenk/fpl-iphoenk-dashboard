# Independent Python xP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task if native execution is selected, or superpowers:subagent-driven-development if delegated execution is selected. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce an independently computed, position-aware experimental next-GW xP model and show validated results beside existing predictions without changing the default model.

**Architecture:** Python acquires and validates Official FPL records, computes a reproducible baseline, and writes an ignored JSON artifact. A trusted Node command publishes it into private Blob; a read-only Vercel route serves only current, valid output. Existing dashboard sections present optional comparisons and immutable forward evaluation.

**Tech Stack:** Python 3.11+ standard library, existing Node.js/JavaScript/CSS, existing @vercel/blob, Node test runner and Python unittest. No new production service, ML library or scheduler.

**Spec:** ../specs/2026-10-20-python-xp-design.md

## Global Constraints

- Official FPL only for the initial computation. Official ep_next and FPLens are comparison baselines, never input features or silent replacements for this engine.
- GK, DEF, MID and FWD use different scoring and relevant statistics.
- Missing is not zero. A previous GW output cannot stand in for a new one.
- Exclude coach/team/formation fit, tactical schemes, subjective skill scores, speculative simulations, calibrated probabilities and invented ranges.
- First release targets the next GW only; no default model replacement or automatic use in transfer/rival simulations.
- Acquisition of all mutable required inputs must complete within one bounded 30-minute collection window. Current output expires six hours after the oldest required mutable-input acquisition, or at its deadline, whichever comes first.
- Publish only before deadline; keep all generated numeric data, caches and tokens outside Git. No browser token or public write route.
- Preserve existing mirrors, immutable archives, approved responsive structure and ten-item pagination. No V6/V12 or new scheduler integration.

## Review Focus

1. A player transferred clubs or changed official position: current identity is validated; unavailable historical club/position evidence must not be reassigned silently (Task 1).
2. A partially finalized DGW: unfinished or unchecked fixtures never enter training, and fixture-level rows are not synthesized by dividing GW totals (Task 1).
3. All appearances or xG values are genuinely zero: keep explicit reported zero; a missing field invalidates the affected calculation (Task 2).
4. Availability/fixture changes after publication: current read suppresses mismatched own-model rows; other providers remain functional (Task 3).
5. Publication and archive races across deadline: server clocks before and after writes gate eligibility; overwrite cannot replace first captured forecast (Task 4).

## File boundaries

- `python_xp/{__init__,__main__,acquire,validate,baseline,evaluate}.py`: command entrypoint, allowlisted acquisition, strict records/scoring, position-aware statistics and matched-cohort evaluation.
- `tests_python/test_{acquire,validate,baseline,evaluate}.py`: small synthetic fixtures declared inline; no live or provider data committed.
- `own-model.mjs`: pure validation, canonical JSON/hash inputs, identity/age/fixture checks, archive conversion.
- `own-model-server.mjs`: private Blob reads and official revalidation; no writes exposed over HTTP.
- `scripts/publish-own-model.mjs`: trusted explicit private publication and predeadline capture; credentials from environment only.
- `own-model-ui.js` and `own-model.css`: optional comparisons in existing sections, no parallel dashboard or default model override.
- Modify `api/index.js`, `phase-one-server.mjs`, `phase-one-ui.js`, `phase-two-ui.js`, `about-ui.js`, both build scripts, `.gitignore`, CI and documentation only where the tasks specify.

## Plan review

Task interfaces match the spec's strict data gates, private publication, next-GW experimental scope and existing-section UI. The live inventory is a mandatory correctness gate: if Official FPL cannot provide a required component unambiguously, stop publication and report the limitation rather than creating a partial total.

Recommended execution: native in this conversation, with one independent whole-branch review before integration. Tasks share validation/schema interfaces; a single implementation owner avoids competing interpretations of missingness and expiry.
